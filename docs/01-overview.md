## 1.1 プロダクト定義

スマートフォンを「現実には見えない存在を映し出す特殊な懐中電灯」に見立てた、ブラウザ上で動作する WebAR ホラーゲーム。

プレイヤーは暗い部屋で端末を構え、背面カメラの映像を見ながら周囲を見回す。
肉眼では何もないが、画面を通すとそこに幽霊がいる。
端末を向けて光を当てている間だけ幽霊は動きを止め、浄化が進む。
光の届かない方向にいる幽霊は、その間も静かに距離を詰めてくる。

### コアループ

```text
どこかで声がする。方向を聞き分ける
        ↓
その方向へ端末を向け、光軸に捉える
        ↓
捉えている間だけ静止し、浄化ゲージが溜まる
  （外せば再び接近を始める）
        ↓
浄化完了 → 少しの静寂 → 次の 1 体が別の方向に現れる
        ↓
3 体目を浄化 → GAME_CLEAR
接近を許して接触 → GAME_OVER
```

**ゴーストは同時に 1 体しか存在しない。**
複数が同時に声を出すと音が混ざり、空間音響で方向を特定できなくなるためである
（[04.1](./04-game-rules.md#41-基本ルール)）。
鳴っている声が常に 1 つであることが、「音で方向を探す」という中心的な体験を成立させている。

「どちらを向くか」という選択が唯一の意思決定であり、
探している間も相手は距離を詰めてくる。ここに緊張が生じる。

## 1.2 設計原則

原典 §38 の「技術的制約を隠そうとせず、制約をゲームルールとして利用する」を本設計の最上位原則とする。

具体的には次の 3 点に現れる。

| 技術的制約 | ゲームルールへの転化 |
| --- | --- |
| DeviceOrientation では回転しか取れず、移動が追えない | プレイヤーは移動しない。世界がプレイヤーを中心とした球面上に配置される |
| カメラの視野は狭く、一度に一方向しか見られない | 見ていない方向の脅威が進行する、という恐怖の source にする |
| Torch の光は前方にしか届かない | 光軸内という限定条件を、静止と浄化の唯一のトリガーにする |

制約を隠すための誤魔化し（見えない位置補正、視野外での挙動停止など）は実装しない。

## 1.3 対象環境

### 主対象

| 項目 | 要件 |
| --- | --- |
| OS | Android |
| ブラウザ | Google Chrome（最新安定版） |
| プロトコル | HTTPS（GitHub Pages が自動提供） |
| グラフィックス | WebGL 2 対応 GPU |

### 必要ハードウェア

| デバイス | 必須 / 任意 | 欠けた場合の挙動 |
| --- | --- | --- |
| 背面カメラ | **必須** | 起動不可（`ERROR_CAMERA`） |
| WebGL 2 | **必須** | 起動不可（`ERROR_WEBGL`） |
| ジャイロ / 加速度センサー | **必須** | 起動不可（`ERROR_SENSOR`）。ただし `?mock=1` 指定時はモック入力で代替 |
| 背面 LED（Torch） | 任意 | 仮想ライトのみで続行。起動時に一度だけ告知 |
| 振動（Vibration API） | 任意 | 振動なしで続行。告知しない |
| Screen Wake Lock | 任意 | 画面消灯を許容して続行。告知しない |
| Fullscreen / Orientation Lock | 任意 | 通常表示で続行。横向き時は回転を促すオーバーレイを表示 |

必須 3 項目以外は、**欠けていてもゲームが成立すること**を設計要件とする。
判定は User-Agent ではなく実 API の capability に対して行う（原典 §26）。

### 非対象

- iOS Safari（`DeviceOrientationEvent.requestPermission()` による明示的許可フローと、Torch API 非対応のため初期スコープ外）
- デスクトップブラウザでの本番プレイ（ただし `?mock=1` による開発検証は正式にサポートする）

## 1.4 スコープ

### 実装する

- 背面カメラのリアルタイム表示
- MediaStreamTrack を用いた Torch 制御
- DeviceOrientation による視点追従（3 自由度・回転のみ）
- Three.js による幽霊の合成表示
- 光軸判定に基づく静止・浄化メカニクス
- 空間音響による方向提示（Web Audio / PannerNode / HRTF）
- DeviceMotion によるシェイク回避アクション
- フルスクリーン・向きロック・Wake Lock
- デバッグ HUD とモック入力
- GitHub Actions による Pages への自動デプロイ

### 実装しない

原典 §36 の除外リストを継承し、さらに本設計で以下を追加除外する。

| 項目 | 除外理由 |
| --- | --- |
| ARCore / WebXR / SLAM / 平面検出 | 原典 §36。本 PoC は 3DoF で体験を成立させることを検証対象とする |
| 画像認識 / 空間メッシュ / AI 物体認識 | 原典 §36 |
| GPS / マルチプレイ / バックエンド / アカウント / DB | 原典 §36 |
| 物理エンジン | 原典 §36。接近は 1 次元の距離減衰のみで表現する |
| 複雑なポストプロセス | 原典 §36・§28。モバイル GPU の熱とフレームレートを優先する |
| PWA / Service Worker | 「インストール不要」がコンセプトであり、オフライン動作の要求がない。キャッシュ制御を持ち込むとデプロイ直後の検証で古い版を掴む事故が起きるため、PoC では明確に不利 |
| 多言語対応（i18n） | UI 文言は日本語固定。抽象化の costs に見合う要求がない |
| アナリティクス / 外部送信 | 原典 §31 のプライバシー方針。カメラ映像に限らず、一切の外部送信を行わない |
| ユーザー位置の追跡（歩行移動の反映） | 原典 §9・§37。3DoF で完結させる |

## 1.5 プライバシー方針

原典 §31 を厳格に適用する。

- カメラ映像は `<video>` 要素への表示以外に一切使用しない
- カメラフレームの取得（`drawImage` / `getImageData` 等）を行わない
- 録画・録音・アップロードを行わない
- ネットワーク送信は、静的アセットの取得を除いて存在しない
- 保存するデータは `localStorage` のクリアタイム記録のみで、端末内に留まる

この方針は実装上の制約として `07` の ESLint ルールにも反映する。

## 1.6 パフォーマンス目標

原典 §27 を踏襲する。

| 指標 | 目標 |
| --- | --- |
| 最低フレームレート | 30 FPS |
| 目標フレームレート | 60 FPS |
| 起動から操作可能まで | 5 秒以内（カメラ許可の応答時間を除く） |

処理の優先順位（フレーム予算が不足した場合に削る順序の逆順）：

1. カメラ映像の表示
2. 姿勢の取得と反映
3. Three.js の描画
4. 幽霊のアニメーション
5. エフェクト

## 1.7 用語集

本設計書を通じて以下の用語を厳密に使い分ける。実装のクラス名・変数名もこれに従う。

| 用語 | 定義 |
| --- | --- |
| **照射（Light）** | ゲームルール上の「光を当てている」状態。物理 LED の点灯とは独立した概念 |
| **Torch** | 物理的な背面 LED。照射状態に追従して点灯を試みるが、成否はゲームに影響しない |
| **光軸（Beam Axis）** | 端末カメラの正面方向を指す単位ベクトル。ワールド座標系で表現する |
| **光錐（Beam Cone）** | 光軸を中心軸とする円錐。この内側が「照らされている」領域 |
| **捕捉（Held）** | 照射 ON かつ光錐内にいる状態。ゴーストは静止し浄化が進む |
| **浄化（Purification）** | 捕捉の継続によってゴーストを消滅させる行為。ゲージで表現する |
| **接近（Approach）** | 捕捉されていないゴーストがプレイヤーとの距離を詰める挙動 |
| **掴みかかり（Grabbing）** | 距離が 0 に達し、シェイクによる振り払いの猶予が与えられている状態 |
| **方位（Angle / Azimuth）** | プレイヤーを原点とする水平面上の角度。ワールド前方を 0 とし、右回りを正とする |
| **キャリブレーション** | 現在の端末の向きをワールド方位 0 として基準化する操作 |
| **モック入力** | `?mock=1` 指定時に、センサーとカメラの代わりに用いる擬似入力 |
