## 設計判断のサマリ

実装に入る前に、本設計を貫く 5 つの判断を示す。

### 1. 物理 Torch とゲーム上の照射を分離する

`LightState`（ゲーム上の照射 ON/OFF）を正とし、物理 LED の制御はそれに追従する従属レイヤとする。
Torch 非対応端末でもゲームが完全に成立し、副次的に PC ブラウザだけでゲームロジックを検証できる。

### 2. 「光軸内にいるかどうか」を唯一のコアメカニクスにする

ゴーストは、照射 ON かつカメラ前方の一定角内にいるときだけ静止し、浄化が進む。
それ以外のゴーストは常に接近し続ける。原典 §37 の「スマートフォンをどちらへ向けたか」を中心に据えるという方針を、ルールとして直接表現したものである。

### 3. ドメイン層をブラウザから切り離す

カメラ・センサー・WebGL を伴う総合動作確認は実機でしか行えず、往復コストが高い。
そこでバグが出やすい計算（姿勢変換、光軸判定、接近、状態遷移）をすべて副作用のない純粋関数として `domain/` に隔離し、Vitest で検証する。

### 4. 実機なしで回せる開発ループを持つ

`?mock=1` でセンサーをマウス入力に、カメラを黒背景に差し替える。
デバッグ機能は本番バンドルに含めるため、Pages 上の本番 URL に対しても実機デバッグができる。

### 5. マルチプレイは本体を巻き込まない

通信は `NetworkPort` の背後に隠し、シングルプレイは外部通信なしで完結させる。
公開シグナリングサーバーは無保証なので、その不調がシングルプレイの
動作に影響しない構造にしてある。

### 6. 安全を演出より優先する

現実の LED を制御できる以上、明滅演出は光過敏性発作のリスクを持つ。
画面・LED とも 3Hz を超える明滅を設計上の禁止事項とし、恐怖は暗闇と空間音響で作る。
