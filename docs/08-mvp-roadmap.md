# 08. MVP ロードマップ

[← 07. ビルドとデプロイ](./07-build-deploy.md) | [目次](./README.md) | [次: 09. 原典との対応表 →](./09-design-md-mapping.md)

## 8.1 方針

原典 §35 の MVP-1〜6 を基礎とし、本設計で追加したゲーム要素（浄化・音響・シェイク）に対応する段階を加える。

段階の並べ方には 2 つの原則を置く。

**第一に、デプロイ経路の疎通を最初に取る。**
本 PoC は実機でしか検証できず、実機に届ける唯一の手段が Pages である。
この経路が通らない限り、どれだけコードを書いても検証できない。
したがって「Pages に何かが表示される」を最初のマイルストーンとする。

**第二に、各段階の終わりに実機で確認できる状態を作る。**
段階の区切りは「コードが書けた」ではなく「実機で何が確認できるか」で定義する。

---

## 8.2 段階一覧

| 段階 | 内容 | 実機で確認できること |
| --- | --- | --- |
| **MVP-0** | 雛形と CI/CD | Pages に画面が出る |
| **MVP-1** | カメラ表示 | 背面カメラの映像が全画面に出る |
| **MVP-2** | Torch と照射状態 | ボタンで LED が点く／非対応端末でも UI が動く |
| **MVP-3** | Three.js の合成 | カメラ映像の上に立方体が浮かぶ |
| **MVP-4** | 姿勢追従 | 端末を回すと立方体が空間に留まる |
| **MVP-5** | ゴーストの表示 | 立方体が幽霊の見た目になる |
| **MVP-6** | コアメカニクス | 光を当てると止まり、外すと近づく |
| **MVP-7** | 勝敗とリトライ | 浄化してクリア、捕まって敗北、もう一度遊べる |
| **MVP-8** | 空間音響 | 音で方向がわかる |
| **MVP-9** | 回避と演出 | 振って振り払える／演出が付く |
| **MVP-10** | 調整と仕上げ | 通して遊べる |

原典の「MVP-6 まで完成すれば PoC 成功」という基準に対応するのは、本ロードマップの **MVP-6** である。
MVP-7 以降は、本設計で追加したゲームとしての完成度に関わる段階。

## MVP-2：Torch と照射状態

原典 §35 の MVP-2 に対応。ただし[Q8 の決定](./09-design-md-mapping.md#92-主要な設計判断)により、
**`LightState` の分離をこの段階で作り込む**。

### 作業

| # | 内容 |
| --- | --- |
| 2-1 | `domain/light/LightState.ts` を実装 |
| 2-2 | `TorchPort` / `MediaTorchAdapter` を実装（[05.2](./05-infrastructure.md#52-torchport-の実装)） |
| 2-3 | `probe()` で capability を検査し、非対応なら一度だけ告知 |
| 2-4 | HUD に照射トグルボタンを配置 |
| 2-5 | `applyConstraints` のキューイング（連打対策） |
| 2-6 | `?notorch=1` で非対応端末を擬似再現できるようにする |
| 2-7 | 非表示時に Torch を確実に消灯（[05.9](./05-infrastructure.md#59-ライフサイクル管理)） |

### 受け入れ基準

- [ ] ボタンで実機の LED が点灯・消灯する
- [ ] ボタンを高速で連打しても状態が壊れない
- [ ] `?notorch=1` で LED は点かないが、`LightState` は正しく切り替わる
- [ ] タブを離れると LED が消える
- [ ] Torch 非対応の告知文言が出る（`?notorch=1` で確認）

> **この段階で `LightState` と `TorchState` の分離を確認しておくこと。**
> 後の段階のゲームロジックはすべて `LightState` の上に乗るため、
> ここで分離が曖昧なまま進むと、後から剥がすのが困難になる。

## 8.3 段階間の依存関係

```text
MVP-0 ──┬─→ MVP-1 ──→ MVP-2
        │      │
        │      └─→ MVP-3 ──→ MVP-4 ──→ MVP-5 ──→ MVP-6 ──→ MVP-7
        │                                            │        │
        │                                            ├─→ MVP-8│
        │                                            │        │
        │                                            └─→ MVP-9┘
        │                                                     │
        └──────────────────────────────────────────→ MVP-10 ←┘
```

MVP-2（Torch）は MVP-3〜5 と独立して進められる。
`LightState` が分離されているため、Torch の実装を待たずにゲームロジックを組める。

MVP-8（音響）と MVP-9（回避）は MVP-7 の後であれば順不同。

### クリティカルパス

```text
MVP-0 → MVP-1 → MVP-3 → MVP-4 → MVP-5 → MVP-6
```

**MVP-4（姿勢追従）が最大のリスク**である。
ここで姿勢変換を誤ると、以降のすべての段階で「なんとなくずれる」症状に悩まされ、
かつ原因の切り分けが困難になる。

したがって MVP-4 では、

- 実装の前にテストを書く
- 受け入れ基準の「一周回して戻る」「横持ちでねじれない」を必ず実機で確認する

この 2 点を省略しない。
