## 10.1 構成

探索する人（ホスト）を、別の端末にいる人が妨害する非対称対戦。

| 役割 | 人数 | 画面 | できること |
| --- | --- | --- | --- |
| **ホスト** | 1 人 | AR（カメラ＋ゴースト） | 従来どおり探索・浄化する |
| **妨害** | 最大 3 人 | 真上からの俯瞰 | 任意の位置で音を鳴らす |

合計 4 人まで。タイトルで「ひとりで遊ぶ／みんなで遊ぶ」を選び、
みんなで遊ぶ場合に「部屋を作る（探索する）／部屋を探す（邪魔をする）」を選ぶ。

2 段構えにしているのは、シングルで遊ぶ人に通信の話を一切見せないためである。

### 勝敗

| 結果 | ホスト | 妨害側 |
| --- | --- | --- |
| ホストが 3 体すべてを浄化 | 勝ち | 負け |
| ホストが捕まる | 負け | 勝ち |

### 妨害音はゲーム状態に影響しない

妨害音はホストを驚かせ、注意をそらすためのものであり、
**ゴーストの挙動を変えない**。

この判断には副次的な効果がある。音が共有シミュレーションの外側にあるため、
「すでに鳴らした音は巻き戻せない」というロールバックの原理的な制約が
問題にならない（[10.5](#105-ロールバック方式による状態同期)）。

## 10.2 部屋コード

相手に伝えるのは **5 文字**だけで済むようにしている。

```text
W A 2 D 7
```

PeerJS は既定で長い UUID を割り当てるが、それを読み上げるのは現実的でない。
そこで自前の短いコードを生成し、接頭辞を付けたものを PeerJS の ID として指定する。

```text
部屋コード  WA2D7
PeerJS ID   ghostar-WA2D7
```

接頭辞を付けるのは、公開サーバー上の他のアプリと ID が衝突するのを避けるため。

### 使う文字

```text
2 3 4 5 6 7 8 9 A B C D E F G H J K M N P Q R S T U V W X Y Z
```

`0` `O` `1` `I` `L` を除いている。口頭でも画面上でも取り違えるためである。

### 入力の正規化

小文字入力と、空白・ハイフンの混入だけを救う。

```text
"wa-2d 7"  →  "WA2D7"
```

アルファベットに含まれない文字（`0` や `O` など）は**落とす**。
これらは正解が存在しない打ち間違いであり、推測で別の文字へ寄せると、
正しいコードを誤ったコードへ変えてしまう危険がある。落とした結果は
長さ不足となり、入室ボタンが押せないまま入力し直しを促せる。

## 10.3 通信方式

### PeerJS を使う理由

サーバーを立てずに端末どうしを直接つなぐため。
公開シグナリングサーバーは無料で使え、[36](./original-design.md) が禁じた
「バックエンドの構築」にも抵触しない。

```text
端末 A ──┐                      ┌── 端末 B
         ├→ 公開サーバー（相手の居場所を教え合うだけ）
端末 A ←─┘                      └→ 端末 B
         ↓
    確立後は直接接続（P2P）
    ゲームのデータは公開サーバーを通らない
```

### 前提と割り切り

公開サーバーは**無保証**である。落ちていれば接続できない。
その場合はエラーを表示し、シングルプレイは従来どおり遊べるようにしてある。
マルチプレイの不調がシングルプレイを巻き込まないことを設計要件とする。

### 層の分離

`application` は PeerJS を知らない。`NetworkPort` の背後に隠す
（[02.2](./02-architecture.md#22-レイヤ構成)）。
これにより、通信を張らない `NullNetworkAdapter` に差し替えるだけで
妨害側の画面を 1 台で確認できる（[10.9](#109-1-台での確認)）。

## 10.4 受信データの検証

**回線の向こうから来た値は、型では守れない。**

TypeScript の型が保証するのは自分のコードの中だけであり、
相手の端末から届いた JSON は実質 `any` である。相手が改造されている
可能性も、こちらと違うバージョンである可能性もある。

そこで `parseMessage()` を通ったものだけを上位へ渡す。

```typescript
export function parseMessage(raw: unknown): NetMessage | null;
```

想定外なら `null` を返し、呼び出し側は「無視してよい雑音」として扱う。
壊れた入力で例外が飛ぶことはない。

特に次の 2 つは必ず弾く。

| 値 | 弾く理由 |
| --- | --- |
| `NaN` / `Infinity` | 座標計算や描画に流れ込むと画面が壊れる |
| 未知の列挙値 | `switch` の分岐から漏れて未定義の挙動になる |

`purify` のように範囲が決まっている値は、拒否ではなく**丸める**。
多少おかしな値で描画が乱れるより、範囲に収めて動かし続ける方がよい。

## 10.5 ロールバック方式による状態同期

### 適用範囲について

ロールバックが成立する条件は「決定論的な共有状態を、過去から再計算できる」
ことである。本作にこれを当てはめると次のようになる。

| 対象 | ロールバックできるか |
| --- | --- |
| ゴーストの位置・状態 | **できる**。妨害側にも表示するため共有状態であり、再計算も可能 |
| ホストの端末の向き | できない。センサー由来の非決定論的な入力で、再現も予測もできない |
| すでに鳴った音 | できない。音は巻き戻せない |

したがってロールバックは**ゴーストの状態に対して**適用する。
向きは届いた値を保持するだけとし、外挿しない（後述）。
音は共有シミュレーションの外側にあるため([10.1](#妨害音はゲーム状態に影響しない))、
巻き戻せないことが問題にならない。

### 仕組み

```text
ホスト（権威）
  20Hz でスナップショットを配信
        │
        ▼
妨害側
  ├─ 届くまでの間は手元で世界を進める（予測）
  │
  └─ 遅れて届いたスナップショットが過去のものだったら
       その tick まで巻き戻す
       権威の状態で置き換える
       現在まで再シミュレートする
```

これが成立するのは、世界を進める関数が純粋だからである
（[02.2](./02-architecture.md#22-レイヤ構成)）。同じ入力から同じ出力が
得られるため、過去からやり直しても結果が一致する。

```typescript
export function reconcile<S>(
  history: readonly Snapshot<S>[],
  authoritative: Snapshot<S>,
  currentTick: number,
  advance: Advance<S>,
  maxHistory?: number,
): RollbackResult<S>;
```

履歴に残っていないほど古いスナップショットは適用できない。
その場合は巻き戻しを諦め、現在の予測を維持する（`dropped` が立つ）。
既定で 6 秒ぶんの履歴を持つため、通常の遅延では起こらない。

### 向きを外挿しない理由

ゴーストの位置は物理法則に従って進むので予測できるが、
**ホストの向きは人の手の動きであり、予測できない**。

外挿すると、実際には止まっているのに光が動き続ける、といった
誤った情報を妨害側に与えてしまう。届いた値を保持し、
次のスナップショットで更新する方が正確である。

### 通信量

| 項目 | 値 |
| --- | --- |
| tick | 50ms（20Hz） |
| 送信契機 | tick が進んだときのみ |
| 1 回の内容 | 向き 1、照射 1、ゴースト 1〜3 体、経過、残数、速度 |

描画が 60fps でも送信は 20Hz に保たれる。
スナップショットに実効接近速度を含めているのは、妨害側に再計算させず
予測を正確にするためである。

## 10.6 妨害音のクールダウン

1 回鳴らしてから **5 秒**は次を鳴らせない。

### 両側で判定する

| 場所 | 目的 |
| --- | --- |
| 妨害側 | 通信を待たずボタンが反応する。無駄な送信も減る |
| **ホスト側** | **改造した相手に連打させない** |

同じ純粋関数を両側で使うため、判定がずれることはない。
ホスト側は**相手が申告した時刻ではなく自分の時計で**判定する。
相手の時計は信用できない。

クールダウンは**相手ごとに独立**している。1 人が使い切っても
他の人は妨げられない。

### 弾かれたときは状態を更新しない

連打しても待ち時間が延びない。最初の受理から 5 秒で必ず解ける。

## 10.7 妨害側の画面

```text
        12 時 = ワールドの正面
              │
      ╭───────┼───────╮
      │       │       │
      │    ╭──┴──╮    │     ● ホスト（中心）
      │    │  ●  │    │     ◗ 懐中電灯の光
      │    ╰─────╯    │     ○ ゴースト
      │        ◗      │     ◎ 鳴らした音の波紋
      ╰───────────────╯
   ［ノック］［落とす］［足音］［転がす］［ガラス］
```

画面の 12 時方向がワールドの方位 0 に対応する。
ホストが端末を右へ向ければ、光の扇は時計回りに動く。

### Three.js を使わない

2D の図形しか描かないため Canvas 2D で十分軽い。
妨害側の端末に WebGL を要求しない利点もある。

### 座標変換

タップ位置の取り違えは「狙った場所と違うところで音が鳴る」という形で
現れ、目視では気づきにくい。そのため変換は純粋関数として
`domain/multiplayer/TopDownView.ts` に置き、テストで押さえている。

```text
ワールド      画面
-Z（正面）  → 上（12 時）
+X（右）    → 右
+Z（背後）  → 下
```

### 操作

1. 下部のボタンで鳴らしたい音を選ぶ
2. 円の内側をタップする
3. その位置からホストの端末で音が鳴る

円の外側のタップは無視する。クールダウン中のタップも無視する。
ボタンは残り時間を塗りで示し、数字も併記する。

## 10.8 妨害音の扱い

### 音源の配置

mp3 をそのまま置かず、**base64 の TypeScript モジュール**として埋め込む。
同じファイルのまま参照できる形でリポジトリに置かない方針による。

```text
src/infrastructure/audio/sounds/data.ts   （自動生成・約 440KB）
```

差し替えは次のコマンドで再生成する。

```bash
npm run encode:sounds -- <mp3 を置いたディレクトリ>
```

生成されるのは 1 音につき **1 本の文字列リテラル**である。
`+` で連結する形にすると AST が深くなりすぎ、構文解析がスタックを
使い果たす（実際に ESLint が停止した）。

### ホストだけが読み込む

音を鳴らすのはホストだけなので、動的 `import` にして
**妨害側の端末では取得されない**ようにしている。
ビルド結果でも独立したチャンクに分かれる。

```text
dist/assets/data-*.js   424KB   ← ホストのみ取得
```

### 空間音響

再生時は必ず**モノラル化**してから `PannerNode`(HRTF) へ渡す。
ステレオのまま渡すと、ファイルが持つ左右の音像と HRTF の定位が干渉し、
方向が曖昧になる（[05.5](./05-infrastructure.md#音声ファイルの扱い)）。

音は妨害側が指定したワールド座標から鳴るため、ホストは
「どの方向で音がしたか」を聞き分けられる。

### ボタン名

`src/presentation/IntruderView.ts` の `SOUND_LABELS` に集約している。
音とボタン名の対応を直す場合はここだけ変更すればよい。

## 10.9 1 台での確認

`?intruder=1` を付けると、通信を張らずに妨害側の画面を表示する。

```text
https://sakanayuki.github.io/cc_ghostar/?intruder=1
```

合成データでホストの向きとゴーストが動き、音の選択・タップ・クールダウンも
本番と同じように動作する。回線だけを `NullNetworkAdapter` に差し替えて
本番と同じ `IntruderSession` を使っているためである。

2 台用意しなくても、真上視点の見た目と操作感を調整できる。

## 10.10 未検証事項

**実際の P2P 接続は未検証である。**

開発環境から PeerJS 公開サーバーへの WebSocket 接続が確立できず
（HTTPS は到達するが WebSocket がプロキシを通らない）、
2 端末での結合確認を行えていない。

代わりに次を確認している。

| 対象 | 方法 |
| --- | --- |
| プロトコルの論理 | ホストと妨害側のセッションを直結した結合テスト |
| ロールバック | 遅れて届いたスナップショットでの巻き戻しをテスト |
| クールダウン | 両側の判定と、相手ごとの独立性をテスト |
| 受信データの検証 | 壊れた入力・NaN・未知の列挙値をテスト |
| 画面と操作 | `?intruder=1` による 1 台での確認 |
| 接続失敗時の挙動 | 公開サーバーへ繋がらない状況で、エラー表示に落ちることを確認 |

実機 2 台での確認時に見るべき点は次のとおり。

- 部屋コードで実際に繋がるか
- 光の扇がホストの動きに追従しているか（遅延の体感）
- タップした位置から音が聞こえるか
- 4 人目が弾かれるか
